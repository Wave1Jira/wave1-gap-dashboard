Does the Q3 plan meet Quarterly Planning — Lite?

The full quarterly-planning flow assumes story-pointable, sprint-committable work. Provider Directory is vendor-dependent and analysis-heavy — most of its work cannot be pointed or committed, which is exactly why it's moving to Kanban. The Lite track exists for this profile: it keeps the planning intent (initiatives, epics, a roadmap, a visible board) while dropping sprint-capacity commitment.

Conditional pass

Provider Directory satisfies the Lite bar in principle — with four gaps to close before the Epics-Defined gate.

The work genuinely fits a flow-based plan, and a roadmap already exists. What's missing is structural, not conceptual: no initiatives or framework epics exist yet, the Kanban board still needs to be created and configured, and flow metrics have no baseline. None of these block the approach; they are the to-do list.

Why Kanban is the right fit for this work

  • Most of the work can't be planned in two-week chunks. Vendor releases land with ~2 days' notice; analysis items take many meetings over months. There's nothing to commit to a sprint.
  • It isn't story-pointable. The work is analysis, requirements, and testing — not build. Forcing it into pointed, committed stories created the "every story is really a task" distortion the team flagged.
  • Kanban matches the rhythm: pull work when capacity frees up, limit work in progress, and make vendor-wait time visible — instead of committing capacity the team doesn't control.
What changes vs. what doesn't. Provider Directory work moves off the Scheduling sprint onto its own Kanban board, planning shifts from sprint commitment to continuous pull, and metrics shift from velocity to flow. The team, the standup, and the scheduling relationship do not change.

The Waiting on vendor column maps to the Working Agreement's External Dependency Hold overlay. Items parked there (Fabric not done, can't proceed) stay visible but are excluded from active WIP and from cycle-time — so the board shows reality without punishing the team for vendor delay.

2 · WIP limits for a 3-person team

  • Keep limits tight and honest. With ~3 contributors and typically 3–4 active items, set per-person in-progress to 1–2 and total active to about 5. The limit is a forcing function, not an aspiration.
  • One expedite slot. Fabric's ~2-day release notice is an Expedite class of service: a single time-critical spot-check/test item may jump the queue and temporarily exceed WIP. One at a time — if a second expedite appears, something else stops.

5 · Suggested initiative / epic spine

  • Initiative — "Determine the future path of Provider Directory" → Epic Implement Provider Finder migration. Keeps the epic tied to a real customer outcome (the directory goes live on the new platform) rather than a "requirements" placeholder.
  • Initiative — "Run the Business / Keep the Lights On" → Epics Fabric Feature & Site Expansion, Provider 360 Support, Directory Cleanup.
  • Initiatives — Brado, Yext → created as awareness now; epics defined only if/when they're approved to proceed.
Epics stay outcome-based with no time-box. That's deliberate — it's the standards owner's call to resist Q1-epic / Q2-epic patterns, and it's the right one. An epic completes when the outcome ships, not when a quarter ends.

6 · Ceremonies — what changes, what doesn't

  • Keep one shared standup with the rest of the team — run Provider Directory off the new Kanban board, switch to the Scrum board for the scheduling portion.
  • Replace sprint planning with replenishment. A lightweight weekly pull/prioritize (can ride the existing standup's 16th minute) instead of committing a sprint of capacity.
  • Retro stays per the Working Agreement.
  • Quarterly = a roadmap refresh (Now / Next / Later / Future), not a capacity commit.

Kanban in Jira — a Scrum Master's starter path

A short, ordered path for any Scrum Master standing up a Kanban board in Jira: build the board, set WIP, add swimlanes, then turn on flow metrics. Official Atlassian docs first, with video walk-throughs alongside.

1

Build the board

Create a Kanban board, then set columns to match the real workflow — Backlog → Ready → In progress → Waiting on vendor → Validation → Done.

2

Set WIP limits

Add min/max limits per column so bottlenecks surface early. Key constraint: in Jira, WIP limits apply per column, not per swimlane — the limits live on the columns, swimlanes just group the view.

DocsAtlassian — How to do Kanban with Jira (WIP & columns)↗ SearchYouTube — “Jira Kanban WIP limits tutorial”↗
3

Add swimlanes & classes of service

Group the board by class of service — an Expedite lane for time-critical vendor work (driven by a JQL query or priority), plus project and run-the-business lanes.

DocsAtlassian — Configure swimlanes (JQL-based)↗ Search“Jira Kanban classes of service swimlanes”↗
4

Turn on flow metrics

Replace velocity with cycle time, throughput, WIP, and the cumulative flow diagram. Define the commitment point (when an item leaves Ready) so cycle time measures the right window.

Rule of thumb: columns hold the WIP limits, swimlanes hold the classes of service, and the commitment point is where cycle time starts. Get those three right and the rest is tuning.
