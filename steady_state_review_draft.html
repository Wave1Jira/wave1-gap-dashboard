Automation Steady State Operating Model

Status Draft for team review Epic 2026 DACOE Steady State Tracked under AUTO-1233 Feedback due — set date —

Purpose

Why this model is being proposed.

The Automation team needs a consistent way to handle findings raised by daily monitoring once an automation has left Hypercare and entered Steady State. The proposed model is intended to:

  • Remove the need to clone Steady State stories into every sprint.
  • Create Jira work only when the daily monitoring report identifies something actionable.
  • Give the team a repeatable method for choosing the right work type.
  • Capture why findings occur, so the team can report on trends rather than incidents.
  • Keep traceability from the monitoring report through to resolution.

Current-state challenge

What happens today. Described as process, not performance.

  • Steady State monitoring has been represented by recurring or cloned Jira stories.
  • Stories stay open, or are recreated, even when there is no actionable work behind them.
  • There is no documented method for deciding whether a finding becomes a Bug, Story, or Spike.
  • Root causes are not captured consistently, so recurring problems are hard to see.
  • The result is administrative overhead and limited visibility into operational trends.

Guiding principle

The one sentence the rest of the model follows from.

Monitoring identifies work. It does not perform the work.

Reviewing the daily report is an operational governance activity. It does not, by itself, require a Jira issue.

Decision flow

From the daily monitoring report through to the Steady State Epic.

Narrative walkthrough

The same flow in words, for anyone reading without the diagram.

  1. Review the daily monitoring report. This is a standing operational activity. It does not require its own Jira issue.
  2. Decide whether the finding requires action. Expected behaviour, false alerts, informational results, and issues that resolved on their own end here as No Action. Record them if the record is useful for reporting; otherwise close them.
  3. Choose the work type. If function is broken, raise a Bug. If nothing is broken but something new or improved is needed, raise a Story. If the team cannot yet tell which, raise a Spike.
  4. Assign the root cause. Independent of the work type. For a Spike it stays unassigned until the investigation concludes, then it is set alongside whatever follow-up work the Spike produces.
  5. Link to the Epic and prioritise. Work is associated with the 2026 DACOE Steady State Epic and prioritised through the team's normal backlog process. If the finding turns out to be a substantial new initiative, it moves to the appropriate delivery Epic instead.
Spikes feed back into the flow. A Spike does not end the process. Its documented conclusion re-enters at step 3 and produces a Bug, a Story, or a decision that no further work is needed.

Choosing the work type

Applies to findings raised by Steady State monitoring. For general AUTO definitions, see the Jira Work Type Reference tab.

OutcomeWhen to use itExample
No Action Expected behaviour, a false alert, an informational finding, or an issue that resolved without intervention. No Jira work item is created. A temporary delay triggered an alert, but the automation completed successfully.
Bug An existing automation is no longer doing what it did before, and corrective work is required. The cause may be internal, upstream, or environmental — the work type describes the fix, not the blame. An application field changed and the process can no longer complete. A service account credential expired and the run failed.
Story The automation works as designed, but a new capability, exception path, business requirement, documentation update, or proactive improvement is needed. A new business scenario was introduced that the automation was never built to process. A playbook needs updating for Steady State support.
Spike The cause, scope, or correct work type is not yet known and investigation is required. Time-boxed. Produces a documented conclusion and recommendation. Intermittent failures with no clear pattern across code, infrastructure, credentials, data, or an upstream dependency.
Why there is no Task. AUTO does not offer a Task issue type. Operational and maintenance findings route to Bug when function is broken and Story when it is not. Sub-tasks break down an item after it has been created; they are not a triage outcome and do not appear in this flow.

Spike completion expectations

Minimum content before a Steady State Spike can be closed.

  • A clearly stated question or problem to investigate.
  • The evidence reviewed.
  • The root cause, if it was determined.
  • Business or operational impact.
  • A recommended next step and the resulting work type.
  • Links to any follow-up Bug or Story.
  • A clear conclusion — including No Action, where that is the honest outcome.

AUTO work item types

Reference copy. The canonical version lives on the Work Item Types page — transclude it rather than maintaining two copies.

Story

What
Tracks a deliverable that adds value — functionality, documentation, or an operational improvement. Expressed as a user goal where one applies.
How
Must have clear Acceptance Criteria defining when the work is Done.
When
Building known requirements or enhancements.
Example
AUTO-1232 Playbook — Referral Attachment. Creates documentation for a specific automation to support Steady State.

Spike

What
A time-boxed research activity used to reduce uncertainty or investigate a technical approach.
How
The outcome is information or a decision, not functional code. Often produces new Stories.
When
The team lacks enough information to estimate or design a solution.
Example
AUTO-1233 Enhance Automation Steady State Workflow. Researches and recommends improvements to production issue triage.

Bug

What
A problem, error, or deviation from intended behaviour or acceptance criteria.
How
Defined by intended behaviour versus actual behaviour.
When
Existing functionality is broken or was built incorrectly. Often identified during Steady State monitoring.
Example
AUTO-1210 LocAuth — validate and update selectors. Fixed a failure where selectors no longer matched the application UI.

Sub-task

What
A small, technical piece of work that is part of a larger Story, Bug, or Spike.
How
Breaks the "how" of the parent issue into manageable developer steps.
When
Tracking the individual steps required to complete a parent work item.
Example
AUTO-1002 Claim Denials Phase 2 — Update Playbook. Documentation component of a larger delivery Story.

Root-cause categories

The work type says how the work will be managed. The root cause says why the finding happened. They are recorded independently.

Internal Solution Defect

Our code, configuration, logic, or implementation was incorrect or did not behave as intended.

  • Incorrect business rule
  • Code defect
  • Configuration error
  • Logic failed for a scenario that should have been supported
  • Testing did not catch it before release

Upstream Change

A vendor, source system, interface, or business process changed and affected the automation.

  • Vendor application update
  • API response changed
  • Screen layout changed
  • Business team changed the source process
  • Input file structure changed

Design Gap

The automation works as originally designed, but the design did not include a scenario that is now required.

  • New exception path
  • Newly identified business scenario
  • New user population
  • A condition that was not known during design

Environment or Data

Infrastructure, access, credentials, connectivity, platform availability, scheduling, or input data quality.

  • Expired credential
  • Missing permission
  • Network outage
  • Bad or incomplete input data
  • Orchestrator or server availability
  • Locked account

Other

Use only when none of the categories above accurately describes the finding. A short written description is required when this is selected.

Notice that the first three rows are all Bugs with three different causes. That separation is the point: the work type drives how the team manages the work, the root cause drives what the team learns.

What the categories let the team ask

  • Are most incidents caused by our own code?
  • Are upstream systems breaking us, and which ones?
  • Are scenarios being missed during design?
  • Are infrastructure and access issues becoming more common?
  • Are credentials and permissions a recurring problem?

Select only the metrics that will change a decision. Everything else is reporting overhead.
